## 关键结果

现有入口分工如下：

| 目标 | 现有入口 | 口径 |
| --- | --- | --- |
| 生成 SELECT candidate-pool miss 审计候选 | `scripts/analyze_select_ambiguity_bound.py` | 输出 hard NegRank、candidate-pool upper bound 和待人工审计 TSV；upper bound 只是诊断，不是论文主 metric。 |
| 将人工审计结果应用到已有 eval JSON | `scripts/apply_select_multianswer_audit.py` | 对 `audit_decision=valid_multi_answer` 的 `neg_best` 计入 audited soft / multi-answer NegRank，同时保留 hard NegRank。 |
| 把人工审计标签写回 E4 JSONL | `scripts/materialize_select_multianswer_labels.py` | 将有效替代负例写入 `valid_negatives`，并记录 `metadata.select_multianswer_audit`。 |

当前口径边界：

- 主表 Hard NegRank 仍应使用 `NegRankAcc`，只接受原始 `gold_neg`。
- Multi-answer NegRank 只应来自人工审计后的 valid negatives，不能直接等同于 candidate-pool upper bound。
- `analyze_select_ambiguity_bound.py` 的 candidate-pool upper bound 可用于发现标签边界问题，但只能写成 diagnostic upper bound。
- 若将审计标签 materialize 回数据，应同时保留原始 `gold_neg` 与新增 `valid_negatives`，不能覆盖 single-gold label。

## 风险和下一步

风险：

- 本轮未重新运行真实模型评测，也未检查本地 `outputs/select_multianswer_*` 是否完整存在。
- 人工审计 TSV 的 `audit_decision` 是可信度关键；未审计或只按 candidate pool 自动接受的结果不能写成 audited Multi-answer NegRank。
- 若后续导出 release 数据，必须确认 `valid_negatives` 与 `negative_gold_multi` 映射一致，并保留 `negative_gold_single`。

下一步建议：

1. 用小 fixture 或已存在审计 TSV 验证 `apply_select_multianswer_audit.py` 对同一 eval JSON 同时输出 hard 与 audited soft 指标。
2. 在主表 row-spec 中显式绑定 `hard_negrank=NegRankAcc`、`multi_answer_negrank=audited_soft_neg_rank` 的来源文件。
3. release 前跑 `scripts/validate_e4v3_schema.py`，确认 SELECT 样本保留 multi-answer 字段且不丢 single-gold。
